# Assumptions and Limitations

- Airport identity and point coordinates are sourced public reference facts; all operational records, relationships, layouts, incidents, costs, and capacity indicators are synthetic and deterministic from seed `42`.
- The default configured window is 30 synthetic days from `2026-01-01T00:00:00Z`. “Current” is relative to the recorded fixed clock, never wall-clock time.
- GeoJSON airport points are public anchors. All region polygons, terminals, zones, gates, stands, routes, flows, incidents, assets, and energy layers are illustrative synthetic geometry and do not represent boundaries, indoor navigation, security areas, evacuation routes, or restricted areas.
- GeoJSON is packaged into PBIR Azure Maps visuals. No Azure Maps account or customer endpoint is stored.
- Azure Digital Twins deployment is optional through notebook 14 or the local deployment adapter and requires a separately governed runtime endpoint and identity. The current dev runtime uses public network access; private networking is not implemented.
- Live deployment used authenticated Fabric, Power BI, OneLake, Warehouse SQL, Data Agent, Azure Resource Manager, and Azure Digital Twins APIs. Notebooks `00`, `10`, and `11` automate supported Fabric target operations.
- The checked-in sample twin graph is illustrative; notebook `04` produces the configurable synthetic physical graph around all selected reference anchors.
- A `.pbix` is not generated. Source-controlled TMDL and PBIR projects are provided; target definition support and lineage binding are capability-dependent.
- Warehouse cross-database references require the Lakehouse and Warehouse to be in the same supported workspace configuration; a materialization fallback is documented.
- The risk score, data-quality result, synthetic capacity, synthetic cost, and security-control status are walkthrough indicators, not production telemetry or assurance.
- `gold_scenario_kpi` rows for the `optimised` scenario are **modelled projections**, classified `ScenarioProjection`. They are computed from baseline facts by applying documented intervention assumptions; they are not a second simulated world and not observed outcomes.
- The narrow-body turnaround outcome is reported as `NOT_MET`. The modelled baseline is 48.06 min and the optimised projection is 42.48 min against a 39 min target. Closing the remaining 3.5 min would require asserting intervention effect sizes that no source in this repository supports, so the gap is reported rather than removed. Effect sizes in `config/scenarios.json` are never tuned to satisfy a target.
- `validation_idempotency_manifest_production` is scoped to a single orchestration run: the `BASELINE` pass rebuilds it and the `SECOND_RUN` pass compares against it. The guarantee asserted is that identical code and configuration run twice within one orchestration produce identical data. Stability of output across releases is a different and weaker claim, and is not asserted; a deliberate generator or calibration change re-baselines rather than reporting a determinism failure.
- Generators whose output depends on an enumeration index must sort their source rows by business key. Spark does not guarantee Delta read order, so an unsorted read produces the same row count with different values between runs. This was observed in `bronze_asset_inspection` and propagated to `fact_asset_inspection`, `gold_maintenance_kpi`, and `gold_energy_sustainability_kpi`.
- Aggregates that sum `DOUBLE` measures must sum as `DECIMAL` and cast back. Floating-point addition is not associative and Spark does not fix shuffle order, so rounding alone only masks the drift until a value falls near a rounding boundary. This was observed in `gold_commercial_kpi` and `gold_energy_sustainability_kpi`.
- The real-time streaming path is wired end to end: a synthetic producer publishes to eight Event Hubs, one Eventstream per source performs Eventhouse DirectIngestion into the matching raw table, and ingestion is verified by comparing hub sequence numbers with KQL row counts. Two constraints apply. First, Fabric Eventstream rejects `WorkspaceIdentity` for `AzureEventHub` sources and requires `Basic` (shared access key), so local authentication is enabled on the namespace under the scoped, expiring policy exemption `fao-demo-eventstream-sas-waiver`; the producer itself remains keyless on Microsoft Entra. Second, an Eventhouse DirectIngestion destination silently discards `databaseName`, so the destination must reference the KQL **database** item id, and changing it requires recreating the Eventstream because `updateDefinition` does not rebuild the underlying ingestion connection.
- Notebook `10_Deploy_Platform_Artifacts` cannot execute its `execute_warehouse_sql` or `execute_eventhouse_kql` stages inside Spark; both fail immediately while every other stage of the same notebook succeeds. The warehouse stage connects with `ODBC Driver 18 for SQL Server`, which is a plausible but unconfirmed cause. Until it is diagnosed, those two stages are applied out of band by local operator scripts that run the same idempotent scripts in `deployment/manifest.json` order against the same endpoints. Those scripts carry runtime workspace and endpoint identifiers and are therefore deliberately not committed; see [Out-of-band operator scripts](#out-of-band-operator-scripts).
- `warehouse/gold_kpi_checks.sql` fails against the Warehouse database because it references `gold_kpi_daily_summary` without qualification; that object is a Lakehouse table and is not resolvable from the Warehouse. The remaining eight warehouse scripts apply cleanly, so this affects a quality-check script only, not the curated `ops.vw_*` views.
- Fabric job-instance status can remain `InProgress` after the underlying Spark session has failed. Notebook `11` polls job status, so a run can stall until its per-notebook timeout instead of failing fast. Orchestration progress should be confirmed from `orchestration_checkpoint` rows and `spark/livySessions`, not from job status alone.
- Fabric injects job parameters into a cell placed immediately after the cell tagged `parameters`. Any value derived from a parameter inside that tagged cell is computed before the override applies and silently ignores it. Tagged cells therefore contain declarations and imports only; derived values, asserts, and function definitions follow in the next cell.
- The regulatory submission automation outcome is **not modelled**. `config/easa_requirements_matrix.json` carries `matrix_status: BLOCKED_NO_APPROVED_INVENTORY`, `is_synthetic: false`, unassigned compliance/legal/data owners, and `coverage_policy.unverified_rows_contribute_to_coverage: false`. Producing an automation percentage would fabricate regulatory obligations and bypass a deliberate fail-closed control. `gold_scenario_outcome_comparison` reports it as `NOT_EVALUATED` until a named compliance owner approves a submission inventory.
- Recommendations are advisory. There is no autonomous control, no safety-of-flight function, and no command path to ATC, A-SMGCS, AODB, BHS, BMS, aircraft, equipment, or staff.
- No real PII, biometrics, source passenger/workforce identity, credentials, tenant IDs, secrets, or customer operational endpoints are present. Pseudonymous synthetic tokens are excluded from Data Agent grounding.
- Fabric Data Agent and Fabric app item-definition support can vary by target. Source packages are `IMPLEMENTED`; unverified tenant deployment is `BLOCKED` and rejected capability is `UNSUPPORTED`.
- No verified native Rayfin item/API is assumed; Rayfin is implemented as a configurable app module.
- Notebook `14_Deploy_Digital_Twin` deploys the 15-twin sample set only. Its validation contract asserts every `$dtId` starts with `SYN-TWIN-`, so it cannot carry the 1,134-twin, 2,304-relationship 3D scene graph emitted by `deployment/scripts/generate_3d_scenes.py`, whose identifiers follow a `<kind>-<business-key>` convention. The scene graph is applied by an out-of-band operator script that enforces the same DTDL rules but resolves `extends` chains: `MaintenanceAsset` inherits relationships from `Asset`, and a relationship declaring target `Asset` legitimately accepts the `MaintenanceAsset` subtype. Validation that compares model identifiers by equality rejects hundreds of valid relationships.
- The repository does not generate an Azure Digital Twins 3D Scenes Studio configuration document. `digital-twin/3d-scenes/manifest.json` is a build manifest describing the generated geometry, not the Studio configuration. The 18 `.glb` models are uploaded to the `models/` prefix of the `3d-scenes` container and the twin graph is present, but a scene must still be created interactively in 3D Scenes Studio before it renders.
- `3DScenesConfiguration.json` was generated out of band and uploaded directly, which departs from the guidance in `digital-twin/3d-scenes/README.md` that the file is created and maintained through the Studio builder. It validates against the published v1.0.0 schema with zero errors, but that schema is preview-stage and Studio owns the document at runtime: any edit made in the builder rewrites it, and a future Studio release may reject or migrate the generated form. Blob versioning retains the previous version. Regenerating and re-uploading discards anything authored interactively in the meantime.
- `EASASubmissionReview-Dev` is not deployed. The tenant rejects the documented `PaginatedReportDefinition` item format, so the validated RDL source in `paginated-reports/` remains a source artifact only. This is a tenant capability limit, not a defect in the definition.
- `warehouse/13_easa_validation.sql` is not applied by `deployment/scripts/deploy_easa.py`, whose `EASA_SQL` tuple covers scripts `10`, `11`, and `12` only. The EASA schema, views, and row-level security are deployed; the validation script is not.
- `deployment/easa-manifest.json` records intended deployment state, not observed runtime state. It declared `status: DEPLOYED` for the semantic model, interactive report, and both DataPipelines while none of those items existed in the workspace. Deployment state must be confirmed against the live workspace item list or the evidence written to `Files/easa/evidence/deployments/`, never from the manifest alone.
- The scene graph is generated from `digital-twin/estate.json`, a committed snapshot of the Lakehouse reference dimensions exported by `deployment/scripts/export_estate.py`. The generator stays offline and deterministic, and scene identifiers join to Eventhouse business keys only because both derive from that same estate. The snapshot is point-in-time: if the Lakehouse estate is regenerated with different identifiers, the export must be re-run and the scene regenerated and redeployed, or the join silently degrades.
- The eight scene interfaces carry static descriptive metadata; observed operational state exists only on the five `;2` interfaces (`Checkpoint`, `EnergyMeter`, `MaintenanceAsset`, `Gate`, `Terminal`). `Airport`, `Zone`, and `Stand` remain at `;1` because no Eventhouse source keys to them, so no numeric property was invented for them. 3D Scenes Studio visual rules and gauges can bind only to the five kinds that have a source.
- `Queue.waitMinutes`, `Queue.passengerCount`, and `BaggageAsset.healthScore` are declared as DTDL `Telemetry`, which Azure Digital Twins does not store. Telemetry is an event that is routed to endpoints; it never lands on the twin. `instances/sample-twins.json` supplies values for these fields (for example `waitMinutes: 18.4`), and notebook `14` strips them from the twin payload before upsert and posts them to `/telemetry`, where they are discarded unless an event route consumes them. The declared intent is twin state, so these belong on `Property`; DTDL models are immutable, so correcting it requires publishing `;2` interfaces and recreating the affected twins.
- Observed operational state reaches the twin graph only when the out-of-band twin patch script is run. It reads the latest event per business key from the Eventhouse and patches `Checkpoint;2`, `EnergyMeter;2`, `MaintenanceAsset;2`, `Gate;2`, and `Terminal;2` properties. It is a pull-based snapshot, not a subscription: values are as stale as the last run, and `observedAt` carries the source `EventTimestamp` so staleness is visible in the viewer. Nothing subscribes to the Eventstream to update twins continuously.
- Only the entities that have emitted events carry observed state. At the last run that was 144 of 144 checkpoints, 108 of 108 energy meters, 50 gates, 51 gates with incident delay, 35 terminals, and 67 maintenance assets out of 540. Scene elements without a matching event have no observed properties and render statically; that reflects producer coverage, not a mapping defect.
- Azure Digital Twins rejects a colon in `$dtId` with HTTP 400. The Lakehouse carries `terminal_twin_id`, `zone_twin_id`, and `dim_asset.twin_id` values in a `<kind>:<business-key>` form that therefore cannot be deployed as written. Scene twin identifiers use `<kind>-<business-key>` instead, so those Lakehouse columns are descriptive only and are not the deployed identifiers.
- Energy meter identifiers are derived as `MTR-{gate_id}` to match the producer, not taken from `dim_asset`, where the same meter is recorded as `{gate_id}-MTR-ENERGY`. The two conventions disagree; the producer's form is authoritative because it is what reaches the Eventhouse. Checkpoints are likewise derived as `{terminal_id}-CP{n}` because no checkpoint dimension exists.

## Out-of-band operator scripts

Four steps above are performed by local operator scripts rather than by a committed notebook or `deployment/scripts/` entry:

| Step | Purpose |
|---|---|
| Warehouse SQL apply | Runs `deployment/manifest.json` `warehouse_scripts` in order over the runtime SQL endpoint |
| Eventhouse KQL apply | Runs the ordered `eventhouse/` commands over the runtime KQL query URI |
| Scene twin deploy | Upserts the generated 1,134-twin / 2,304-relationship scene graph into Azure Digital Twins |
| Scene twin patch | Pulls the latest Eventhouse event per business key onto the `;2` interfaces |

These scripts embed the runtime workspace GUID and service endpoints, so committing them would breach the repository rule that no tenant identifier, workspace ID, or endpoint appears in source. They are therefore excluded by `.gitignore`. Anyone reproducing the deployment reimplements them against the committed manifests, SQL, KQL, and generator output, which are the authoritative definitions.
